# Cross-cutting decisions and dead ends

What the four integrations share: decisions that must be made once rather
than four times, the checklist a new integration has to satisfy, and one
mechanism that looked general and turned out to have no customers.

## Decisions this wave must open with

1. Capability vocabulary. `Capability` is a closed 2-case enum. GitHub login
   is neither coding agent nor control plane; Tailscale and T3 Connect both
   provide something like private reachability. Each new case must read well
   in the blocked-playlist sentence and get a CONTEXT.md category entry. An
   integration with `provides: []` is legal but can never be a prerequisite.
   Still the first thing to settle.

2. New `FlowPrompt` cases: exactly one, down from the three originally
   planned. URL-plus-displayed-code for the gh device flow, the inverse of
   `.openURLAndEnterCode` - the user types our code into github.com, so it
   needs a copy affordance. The other two evaporated:

   - Open-URL-and-wait is not needed. `tailscale up --json` returns the
     `AuthURL` immediately and `tailscale status --json` keeps serving it,
     so a plain open-URL prompt plus a polling loop is enough. No step ever
     has to drain a PTY behind a visible prompt.
   - Secret entry is not needed. The user chose an ordinary interactive
     Tailscale login over a pasted auth key or OAuth client secret, so
     nothing is ever pasted and the app holds no Tailscale credential.

   T3 Connect needs no new case either: its headless login maps onto the
   existing `.openURLAndEnterCode`.

   So the whole wave adds exactly one prompt case, and it belongs to GitHub.

3. `SpriteAction.Kind.copy(String)` for tailnet addresses, connection
   strings and similar. Deferred from the ui-fixes wave; unchanged.

4. `IntegrationStatus` structured details. T3 smuggles a version into the
   summary string today. Tailscale wants MagicDNS name, tailnet and IPs; gh
   wants the account login and token scopes; Connect wants linked and relay
   state. Consider `details: [(label, value)]`. Every new integration has
   two or more fields worth showing, so this is no longer speculative.

5. Observation cost, now measured on a warm sprite rather than guessed:

   | Probe | Time |
   |---|---|
   | Trivial exec round-trip | 0.28-0.44s |
   | `claude auth status --json` | 0.81-0.92s |
   | One exec testing five file artifacts | 0.39s |

   Integration statuses are awaited serially. Five integrations through CLI
   probes is roughly 4.5s per refresh against about 0.4s batched as file
   probes. Prefer file probes, and consider batching or concurrency before
   the registry grows.

6. Revoke-shaped flows, and they are worse than expected. All flows are
   additive today, and each of the three new integrations fails differently:

   - `gh auth logout` is local-only and does not revoke server-side. gh's
     own help says so, and warns that the manual revoke "will revoke all
     authentication tokens ever generated by the GitHub CLI across all your
     devices".
   - `tailscale logout` leaves the node in the admin console. Revoking an
     auth key does not deauthenticate nodes already joined with it.
   - `t3 connect unlink` and `logout` exit 0 even when the server-side
     revoke fails, printing only prose and a WARN, and `logout` then deletes
     the local credential and strands the retry.

   So the affordance cannot trust an exit code. "Removed locally, NOT
   revoked remotely" has to be a first-class outcome the UI can state.

7. Secrets in argv. Anything secret goes over stdin or through a `file:`
   indirection, never argv: it leaks to `ps aux` and to the exec-session
   list the app itself reads and displays. Tailscale's `--auth-key=file:` is
   the model, and the same rule covers planting a GitHub token or a T3
   credential.

8. Naming. CONTEXT.md bans "connect" as a common noun because it collides
   with the platform's Connectors. "T3 Connect" is the product's proper noun
   and stays, with a glossary entry drawing the line; GitHub tickets say
   "Log in to GitHub".

9. External preconditions fixed in a web console. This shape recurs and has
   no Flow vocabulary today: Tailscale MagicDNS, Tailscale HTTPS
   certificates, Tailscale Serve enablement, ACL tag ownership, and GitHub's
   sudo mode are all "go to this page, change something, come back". It is
   neither a missing capability nor a declined consent. Worth deciding once,
   before three integrations invent three different answers.

10. Integrations recognizing platform tasks the way they recognize Services.
    Deferred future feature; the claude-code-service status endpoint is
    groundwork.

## Glossary work implied

CONTEXT.md changes that follow from the findings, mandatory per
`docs/agents/domain.md`:

- Whether "Saved login" generalizes beyond the one Claude token. GitHub
  gets one; Tailscale deliberately does not; T3 Connect cannot have one.
  The entry is currently written specifically about Claude.
- An explicit note that T3 Connect has no saved login and why, so the
  absence reads as a decision rather than an omission.
- A second, invisible variant of "Pairing": managed T3 Connect still mints
  a pairing grant, but with subject `cloud-connect`, a 2-minute TTL, and no
  human-typable token.
- Whatever new `Capability` cases item 1 settles on.

## What a new integration must implement

- Conform to `Integration`: the seven protocol requirements (id,
  displayName, provides, requires, recognizes, observeStatus, actions,
  flows).
- Register in `Integrations.all`; optionally add a playlist entry. Two
  separate hand-maintained lists.
- Flows: one file per integration, non-interactive steps through the
  capturing exec helper. Note that none of the three new integrations needs
  the Claude PTY pattern - gh, tailscale and t3 all mint through plain
  non-interactive execs, so the TERM/rows/cols dance, the Enter-as-a-
  separate-keystroke trick and the reattach-by-identity logic are all
  Claude-specific.
- Verification doubled: the CLI's own status probe plus the artifact the
  detail screen observes. Note gh breaks the assumption that verification
  costs something - `gh auth status` round-trips the API for free, so it
  needs no consent gate, unlike `claude -p`.
- Tests against the fake platform copying the established suites
  (recognition, flow offering, login-flow scripting, setup idempotence,
  cold-deep-call tripwire), plus a `SPRITES_INTERACTIVE=1` live rig, plus a
  findings entry in this directory.
- A tripwire test for every undocumented surface the integration depends on,
  in the spirit of `ClaudeOutputParser.signInMarker`: it must fail loudly
  when a vendor changes shape. The known ones are `tailscale up --json`
  (explicitly "format subject to change"), `AuthURL` in
  `tailscale status --json`, gh's two stderr lines, and T3's on-disk
  credential schema (which has no version field).

## Dead end: the browser-open channel

Recorded so it is not rediscovered and re-argued.

The base image exports `BROWSER=/.sprite/bin/sprite-browser`, a readable
bash wrapper that does two things with any URL it is handed:

1. Appends a timestamped record to `/tmp/xdg-open.log`, including a
   `FOUND_URL: <url>` line.
2. Emits an OSC escape sequence carrying the URL:
   `ESC ] 9999 ; browser-open ; <URL> ESC \`

It walks the process tree for an ancestor with a TTY and writes there,
falling back through `/dev/tty`, stdout and stderr, so the sequence reaches
our PTY stream in every case, and reaches stdout even in a non-TTY exec.
Both channels were confirmed live through the app's own exec path:

```
$ sprite exec -s <s> --tty -- bash -lc 'sprite-browser "https://example.com/auth?code=abc123"'
^[]9999;browser-open;https://example.com/auth?code=abc123^[\

$ sprite exec -s <s> -- bash -lc 'sprite-browser "https://example.com/nontty"'
^[]9999;browser-open;https://example.com/nontty^[\
```

This looked like a CLI-agnostic replacement for the per-vendor string
anchoring the Claude flow uses (`signInMarker = "didn't open"`), available
without holding a socket. It has no customers:

- Tailscale never touches `$BROWSER`; it prints its own `AuthURL`, in JSON.
- gh under a non-TTY exec - the shape the login flow uses - never invokes it
  at all. Only the interactive TTY path does, after an Enter press, and the
  URL it carries is the bare `https://github.com/login/device` with no code.
- T3 reaches the channel but carries the loopback callback URL
  (`redirect_uri=http://127.0.0.1:34338/callback`), useless on a phone.
- Claude, the one integration already shipping, carries the loopback variant
  here too, which is exactly why its parser deliberately anchors past it.

Every integration prints the URL the user actually needs on its own stdout.
Parsing that is the honest approach, and it is what all four want anyway. Do
not build a shared `BrowserOpenObserver`.

Two details worth keeping even so. The wrapper always exits 0, so "the
browser opened" is never a signal and every flow still needs its own
completion check. And `/tmp/xdg-open.log` is mode 644, world-readable,
append-only and never rotated, which is why the Claude login flow sweeps it -
a Checkpoint would otherwise capture authorize URLs. Only the interactive gh
path writes to it, so gh needs no sweep step.
